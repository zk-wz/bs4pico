# D4：原版游戏的产品交付与基本性能

## 用户成果与依赖

在 [D1](game-runtime.md)运行链、[D2](steam-integration.md)真实服务和 [D3](game-openxr.md)可玩闭环基础上，交付同一 APK 的日常使用路径：选择实例、启动／退出、失败恢复、独立更新和重新安装后按提示恢复资源。不是再建一轮可行性验收；正常路径已经成立的部分直接复用。

本阶段只完成原版产品；LIV／混合现实录制不做，mod 加载留给 [D5](mod-chart-manager.md)。共用 [架构](ARCHITECTURE.md)与实例／启动契约，执行进度维护在 [STATUS](../STATUS.md)。

D4 拥有 [组件契约](COMPONENTS.md)规定的云目录发布、更新消费、安装安全、恢复事务与对应 UI；[component-catalog.json](component-catalog.json) 是未来发布源，不是已上线服务或可下载制品证明。宽目录同时记录禁用、APK 内置、本地／授权用户导入、Steam depot、系统管理及未来远程 bundle，不要求现在实现所有未来功能。

## 实现落点

- 在现有 `prototypes/spatial-openxr/` 产品宿主中完成实例列表、准备／启动状态、设置、失败说明和恢复入口，不新建第二个 APK 或模拟商店。
- 完成 D1 实例安装事务、D2 下载发布与更新、D3 正常退出的统一操作协调；备份、账号及游戏数据不塞进 Android Activity 状态对象。
- 根构建与现有 `build-apk.sh` 的 Android 运行时依赖纳入明确构建入口；将可再分发组件清单／许可证／版本锁和第三方来源一起交付。未来 CI 调用同一本地入口，不引入另一套工具链。
- 启动与 native lifecycle 日志关联 runId/session 和错误阶段，用户可查看当前失败；导出时去掉账号标识与秘密，不启用常开逐帧日志或额外遥测服务。
- 开发相关功能时使用当前主要文档、源码／upstream issue 并搜索现有候选之外的可行方案。云供应商、目录托管／认证、签名信任与密钥轮换策略、模块边界／交付方式，以及重大性能、许可、隐私、维护或体验取舍，集中提供 2～5 个真实选项、证据与推荐并 Ask，等待选择后实施；既定默认与日常编码不重复询问，决策／重开条件和证据记入现有 decisions／STATUS，不另设研究或验证阶段。

## 实现顺序 1：可用的管理页面

1. 收口实际已实现的账号／游戏实例页面：版本、资源状态、Steam 会话、当前运行状态、启动／停止、日志及恢复入口；按钮按实际状态可用，不把 `runtimeReady` 画成游戏已授权。
2. 保存当前实例和已支持设置，游戏启动只读该次不可变配置；运行中更改需明确“下次启动生效”，不能让部分 native 配置在未同步时改变。
3. 按错误阶段给可执行恢复操作：重新授权、恢复未完成准备、选择旧可玩实例或查看实际日志。缺组件就指出其来源和状态，不无限自动重试或默认退回管理而隐藏错误。
4. Spatial 管理场景只在需要时运行；游戏会话不保留背景管理渲染。返回后恢复真实实例和退出结果，不切任意其他 Activity 或系统窗口。
5. 组件列表区分已安装／禁用／本地或系统提供／可下载且兼容／需要用户合法来源／未知兼容性／不支持且需新版 APK。展示目录条目不等于支持安装，未知 schema、能力或 module ID 不执行代码；只有实现的 allowlisted typed installer／loader 才能将“可下载”变成真实操作。

## 实现顺序 2：安装、更新与恢复事务

1. 将 D1 源／备份／工作副本、D2 staging／发布目录与组件快照落实为统一版本化事务：记录准备、已提交、运行占用和失败恢复，不因复制中断留下看似可启动的半实例。
2. 实现经认证的 HTTPS 云目录发布及消费，用真实发布源生成签名目录，验证信任策略、目录签名与制品摘要后才使用；服务供应商／信任政策按上述 Ask 决定，不能交付占位 URL、假更新按钮或未签名替代。离线使用此前验证且已提交的快照；缓存与云 metadata 均不能授予 Steam 权益、跳过真实授权或再分发受限内容。
3. 依共享契约先检查 installer／loader 能力、Android 平台／native ABI、许可证与合法来源，再解析完整兼容 bundle：RuntimeSet 中 Wine／DXVK／Windows XR／Steam PE＋Unix 适配及引擎兼容性成套匹配，SteamBackendBundle 的实际客户端与 bootstrap／service adapter 成对匹配协议。目录可见却无实现能力的条目明确需新版 APK，不盲目加载远程代码。
4. 新版本在独立 staging 获取／校验／组件适配并生成 ResolutionSnapshot，全部就绪后让用户选择，以原子提交激活目录与 `resolutionSnapshotRef`；保留上个已提交快照、旧可玩工作实例及备份。游戏运行时不替换 workRoot／runtimeSet／bundle，不覆盖唯一本地原件，不把目录查询或云处理放进 XR 帧通路。
5. 存档、配置、prefix 与游戏／组件版本分别保留；必要迁移前备份并记录数据兼容性，失败或回退时同时恢复匹配快照及其可兼容的数据状态，不能只退二进制而留下不可逆新数据，也不盲目跨版本复制整个 Wine prefix。
6. 应用进程死亡后下次打开按持久化事务状态恢复 UI，并处理未提交 staging／中断原子提交；只有真实未退出的会话才继续表示运行，旧 runId 的回调／临时文件不能复活旧状态。
7. 对用户发起的删除／释放空间说明将移除哪个工作实例与数据；不默认删除源、备份、凭据或用户其他实例。卸载 Android 应用可能清除私有目录，管理页在导出／重装流程中明确提醒并提供合法资源重新导入方式，不承诺跨卸载自动保留。
8. 只有当前功能需要时修正 Home、失焦、摘戴／重建的恢复；无法继续原歌曲则如实回菜单或重启，不承诺未经实现的无缝现场恢复。

## 实现顺序 3：安装包和可复现构建

1. 产品目标使用 Android arm64-v8a；模拟器诊断 ABI 与产品包清晰分开。检查 ELF 对齐／目标页大小、最低 API、Manifest 和所需组件依赖，不能把 x86_64 模拟器运行当 ARM64 发行依据。
2. ARM64 PE 与 Bionic Unix 半边从锁定源码构建，列出实际使用的补丁／许可证和校验值；专有或受限组件按获准的用户侧准备路径处理，不静默纳入 APK。
3. 单 APK 包含自有 Android 宿主和获准再分发代码；正版游戏、Unity 受限组件、账号会话和私有签名不提交。Android 仅对实现且兼容、合法的组件支持独立更新，不能承诺所有代码远程可加载或 APK 永久冻结。编译在 APK 的账号／协议／下载 SDK 在稳定 provider 边界实际拆分前仍需 APK 更新；新 installer／loader 能力、平台 ABI 或宿主 API 变化亦可能要求新版 APK。APK 升级不重下已有正版内容。
4. 提供实际存在的构建、安装、启动和资源准备命令，更新 [构建说明](../build/README.md)；只有在实现入口存在并被运行后，才把“一键构建／部署”写为已可用。
5. 应用签名通过忽略的本地配置／正常构建环境提供，不把第三方仓库附带签名或用户私钥复制进产品。发行与 debug 配置明确区分，关闭非必需调试开关。

## 实现顺序 4：实际瓶颈的基本优化

1. 沿当前正常游戏会话记录 CPU／GPU 帧时间、主要等待和复制、shader 编译活动及声音表现；按实际证据选瓶颈，不先做多份成本排名或追求上游 FPS。
2. 优先消除管理背景渲染、不必要 mirror blit、每帧日志／异常、额外队列空转和不必要 GPU copy；shader/pipeline 缓存按实际驱动能力实现。
3. 降低镜像成本时保留 Unity／Wine 必要窗口，不能仅因窗口不可见就宣称不再渲染。修正 MSAA 读写／resolve 正确性后再减少无用 stores，不照搬破坏后续 load 的 discard。
4. 配置画质、分辨率、MSAA 和已支持的刷新率，明确硬件／runtime 实际能力。注视点、眼动、动态分辨率等仅在用户要求或实际瓶颈需要时再接，不成为原版交付新依赖。
5. 音频延迟与 XR 帧时间分开处理，出现节拍偏差就在现有游戏输出路径修复；没有测量工具时不写精确毫秒结论。持续热稳定、长时掉帧或重复采样是用户另行指定的专项，不默认追加。

## 随实现进行的轻量交付检查与完成条件

在上述功能实现时复用当前产品路径：从产品 APK 正常打开 Spatial → 选择已准备正版实例／真实 Steam 服务 → 游玩 D3 的同一代表性歌曲 → 正常退出返回管理。只检查 D4 这次改变的恢复／更新必要边界一次，复用已有歌曲行为证据，不建立单独验证阶段，不重跑全部历史场景或为检查另增环境／设备动作。

- 在更新实现中使用真实合法可获取的制品，检查签名／摘要失败、不支持能力需新版 APK、兼容解析、staging／原子提交中断、数据迁移回滚及离线已验证快照的受影响边界；确认旧实例、存档、原件与真实权益不变。没有合法目标版本则明确未覆盖条件，不伪造更新结果。
- APK 实际安装／升级后观察页面、已准备资源和运行入口，不能以文件已生成代替交付。可在缺设备时继续完成构建，但设备交付仍标待验收。
- 必要设备操作只用后台 CLI／已有实例，不自动恢复窗口、截图或抢焦点。必须人工 VR 操作时集中一次 Ask；不默认循环压力、长轮次或多次性能对照。
- 完成须有可安装包、实际可玩与正常返回、真实状态／失败恢复、资源保护、锁定依赖、可复现入口，以及真实签名 HTTPS 目录发布／消费、兼容组件更新 UI、原子快照切换与数据感知回滚；目录库存广度不是所有未来功能已实现。记录已覆盖设备与未覆盖能力，性能结论不超出观察条件。

完成原版交付后，下一阶段才执行 D5。游戏必需能力无法修复时报告具体实现尝试和不可替代缺项，由用户决定继续或停止；不交付假成功、平面替代 VR 或无限前置验证。
